# 910C 上复用现有 BFCL / tau 评测

统一入口仍为 `benchmark/run.sh`：BFCL 调用现有 Qwen FC handler 的
`/v1/completions`，tau 调用现有 `tau2` 模块的 `/v1/chat/completions`。
两种 API 均由原生 **vLLM-Ascend** 提供。没有独立的 SFT runner 或 Transformers HTTP 服务。

## 环境

在 gpu-910c 的 `/home/liyu.468/learning_kvcache` 执行：

```bash
bash benchmark/setup_910c.sh
source benchmark/env.sh
"$PROJECT_PYTHON" benchmark/check_910c.py
```

- vLLM runtime：`/usr/local/miniconda3/envs/kvcache`，继承镜像 CANN、torch_npu、vLLM 0.23 / vLLM-Ascend，仅安装本项目模型注册插件。
- BFCL driver：`/usr/local/miniconda3/envs/kvcache-eval`，隔离旧 BFCL SDK 依赖。
- tau runtime：`benchmark/tau2/.venv-910c`，复用现有固定版本 `v1.0.1`，Retail **114** / Airline **50** 题。
  x86 的 `benchmark/tau2/.venv` 保留，按机器架构选择。
- 方舟 user simulator 和 Retail NL judge 沿用现有 `ARK_API_KEY` 路由。
  910C 的 `TAU2_HTTP_PROXY` 默认京东代理，`NO_PROXY` 保证本地模型直连；其他机器可覆盖该变量。

## Qwen3 prefix 的原生 vLLM 加载

沿用 Qwen3.5 的 `vllm_plugin.py` 注册方式和 residual-prefix attention 分支，
补充 `Qwen3ResidualKVPrefixForCausalLM`。原生 Qwen3/vLLM-Ascend 负责 causal attention、
分页 KV cache、连续批处理和标准 API；只在 attention 输出投影之前加入训练使用的 residual memory。
prefix 不写入请求 KV cache，所有请求共享同一张只读 memory 表。

导出采用 Qwen3.5 相同的“base shards + 独立 prefix shard + weight index”结构：
base shard 使用普通硬链接或复制，FP32 prefix 保持原值，强制检查全部 72 个张量已加载。
没有软链接，也不改训练中的 base/checkpoint。

```bash
# 训练中可执行：仅 CPU 导出，并打印原生 vLLM 启动命令
bash experiment.sh serve qwen3-prefix --checkpoint latest --prepare-only

# 训练结束后运行，正式实验请显式指定最终 checkpoint
bash experiment.sh serve qwen3-prefix --checkpoint /absolute/path/to/checkpoint --device 0
```

服务地址 `http://127.0.0.1:18160/v1`，模型名 `qwen3-kv-prefix`。
默认 TP=1、单 NPU、`max_model_len=65536`、`max_num_seqs=8`、显存比例 0.75，
初始采用 `--enforce-eager`。Qwen3 工具解析器 `hermes`，推理解析器 `qwen3`，thinking 开启。
检测到全量训练进程时拒绝启动服务；不会占用正在训练的设备。

正式实验使用 8 卡数据并行（每卡一份模型、TP=1）：

```bash
bash experiment.sh serve qwen3-prefix --checkpoint /absolute/path/to/checkpoint-500 \
  --data-parallel-size 8 --max-num-seqs 64
```

默认自动选择设备 0..7，也可用 `--device 0,1,2,3,4,5,6,7` 显式指定。
不显式设置 `max_num_batched_tokens`，采用 vLLM 默认调度预算。
BFCL 正式运行将客户端 `--concurrency` 设为 128；tau 每域设为 8，两个域并行。
并发参考 `outputs/prefix_composition_3domain_20260917/eval/rerun_four_models_20260918_135846/base/run_manifest.json` 的实际运行记录。
DP 是 8 份独立模型副本，vLLM 会将并发请求分给不同副本，并在每个副本内做批处理。
切换 DP=8 前先停止 DP=1 服务；两个服务不能同时占同一张卡。

64K 延续此前评测设置；base 原生长度 40960，导出配置扩展到 65536，保持默认 RoPE 频率，不加入 YaRN。
这属于位置外推；已验证真实 NPU 推理，未做满 64K 长度的质量验证。

## 评测命令

先从服务输出取得本次 `export` 目录，填入 `VLLM_MODEL_DIR`：

```bash
VLLM_MODEL_DIR=/absolute/path/to/vllm_exports/checkpoint-N-ctx65536

bash benchmark/run.sh --benchmark bfcl_v3 \
  --openai-base-url http://127.0.0.1:18160/v1 --model qwen3-kv-prefix \
  --bfcl-model-path "$VLLM_MODEL_DIR" --bfcl-categories multi_turn \
  --bfcl-data-dir benchmark/bfcl_v3/data/envscaler_v3 \
  --temperature 0.7 --concurrency 128 \
  --output-dir outputs/eval_qwen3_prefix/bfcl_v3

bash benchmark/run.sh --benchmark tau2 --tau2-domain retail \
  --openai-base-url http://127.0.0.1:18160/v1 --model qwen3-kv-prefix \
  --tau2-agent-thinking --temperature 0.7 --top-p 0.95 \
  --llm-max-completion-tokens 16384 --tau2-max-steps 200 --concurrency 8 \
  --tau2-require-external-user --tau2-require-external-judge \
  --output-dir outputs/eval_qwen3_prefix/tau_retail
```

Airline 将 `--tau2-domain` 改为 `airline`，并使用独立结果目录。
BFCL 生成上限沿用已有官方 handler 的 4096 tokens；tau user 上限沿用已有模块的 4096。
用户模拟器/评分模型沿用方舟 `deepseek-v4-pro-ga-260813`，与论文 GPT-4.1 设置有差异。

CPU 依赖、任务加载、checkpoint、prefix 数学一致性检查已通过；
结果保存在 `benchmark/runtime/910c_readiness.json` 和 `diagnostics/910c_eval_20261102/`。
训练已按用户要求停止在 step 508，评测固定加载 `checkpoint-500`。
原生 vLLM-Ascend 已加载全部 72 个 prefix 张量，两个标准 API 均已验证。
零售、航空各 1 题的小样本测试均成功（reward=1），不能代表全量成绩。
